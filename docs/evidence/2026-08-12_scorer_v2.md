### Operational note (memory tuning, not a scoring change)

The first resume attempt (4 workers, `MemoryMax=8G`/`MemoryHigh=6G`, no swap limit) caused
system-wide swap exhaustion rather than the intended per-cgroup throttling — `MemoryMax`/
`MemoryHigh` don't constrain swap without a separate `MemorySwapMax`, so the job quietly pushed
8GB into system swap and starved the rest of the desktop. Stopped cleanly (no cache corruption).
A follow-up with `MemorySwapMax=0` traded that failure for a different one: near-total stall,
since anonymous memory over `memory.high` has nowhere to go without swap. Both were
concurrency-driven, not a general per-task leak — the root cause was a handful of atypically
large APKs landing in the same worker window. Fix: split the remaining queue into 585
normal-sized files (2 workers, `MemoryMax=8G`/`MemoryHigh=6G`/`MemorySwapMax=1G`; completed in
704s, 1.20s/APK effective, zero memory incidents) and 15 files >50MB, processed one at a time via
`harness/process_large_outliers.sh` with a dedicated budget and a hard 300s timeout each; 14/15
completed in under a minute in isolation (confirming the instability was about concurrency, not
these files individually), and the 172MB file above was the sole holdout.

**Deviation from the original task brief, noted per instruction**: Task 1 specified
`setuguard_ps1/feature_extract.py` with CLI `--corpus-dir --sample-n --seed --limit --workers
--out-dir`. What exists is `harness/extract_features_pool.py` with `--sample-list --workers
--benchmark --n`, built and partially run (95/716) in an earlier, uncommitted session that was
interrupted (OOM-killed) before finishing or committing. This session verified that prior work
(scorer deletions, sample-set reproducibility, cache integrity, AUC-direction correctness — see
`SESSION_LOG.md`) rather than rebuilding to the literal spec, on the judgment that the harness
location/CLI-naming is a cosmetic difference and the deliverable — a correct, reusable,
sha256-keyed feature cache plus the gate measurement — is unaffected.

## AUC — the gate

Method: Mann-Whitney U / rank-sum identity (exact, matches `sklearn.metrics.roc_auc_score` for
the binary case). Positive class = malicious; higher score = more suspicious. Direction verified
on synthetic cases (positives-scored-higher → 1.0, positives-scored-lower → 0.0, all-tied → 0.5)
and cross-checked against an independent brute-force O(n·m) pairwise implementation on a random
60-malicious-vs-16-holdout subsample, which matched to 4 decimal places (0.4589 both ways).

| | Old | New |
|---|---|---|
| **AUC(malicious vs banking_holdout_16) — THE GATE** | **0.3841** | **0.4113** |
| AUC(malicious vs fdroid_benign) | 0.8736 | 0.9366 |

**Malware does not rank above legitimate banking apps under either scorer** (AUC 0.3841 old,
0.4113 new, both ≤ 0.5 against `banking_holdout_16`); the three deletions improved the ranking
gap by +0.0272 without closing it.
